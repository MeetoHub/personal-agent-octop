# 超级个人智能体 · 设计与施工（2026-11-22）

## 0. 一句话

**不新造概念**：超级个人智能体 = Octop 的 **team host**（团队主持）+ 一个「招人」工具 + 主入口标记。
专家继续是**有记忆的真 agent**，子智能体继续用 Octop 原生的 subagents。我们只补三个缺口。

## 1. 先回答：Octop 的「团队模式」是什么

Octop 里 `kind=team` 的 agent 是**团队主持**：

- 它自己是一个 agent，有一份系统提示（`host_system_prompt`）；
- 它挂一份成员名册（至少 2 个专家）；
- 它的工具被裁剪成 `agent_list` / `ask_agent` / `memory_search` / `memory_get` / `current_time`（`HOST_TOOLS_ALLOWED`）；
- 用户在对话里跟它说话，它负责**派活给成员**并把结果转述回来（`wire_host_dispatch`）。

换句话说：**它就是"一个入口、多个有记忆的专家"的现成实现**——正是我们要的东西，只是它默认需要预先建好成员，而且不是默认入口。

## 2. 目标模型

```
用户打开 → 只看到它（超级个人智能体）
             ├─ 会越来越懂你（自己的记忆持续累积）
             ├─ 能招人：agent_create → 有记忆的队员（kind=expert）
             ├─ 队员能带子智能体：Octop 原生 subagents
             ├─ 派活：ask_agent（已有）
             └─ 长任务：tickets（已有）+「活」页（已有）
平台上可见：它招的队员、队员的子智能体、每个人的记忆和线程
```

## 3. 缺口与改法

| 缺口 | 改法 | 状态 |
|---|---|---|
| 超级智能体没有"招人"的手 | 新增 `agent_create` 工具，仅在**团队主持**或 `config.is_primary` 的 agent 上挂载 | 本次已实现 |
| 没有"谁是主入口" | `agents.config_json.is_primary = true`；前端 `/chat` 默认进它 | 标记已支持，前端待接 |
| 分不清谁是它招的 | 新建 agent 的 `config.created_by_agent_id` 记血缘；团队页按此分组 | 本次已实现（写入），页面待做 |
| 团队必须有 2 个成员 | 主智能体允许 0 队员起步（后续用 `agent_create` 长出来） | 待做（`TEAM_MIN_MEMBERS` 对主智能体放宽） |

## 4. 护栏（写死，不做成配置）

- **只能建在自己名下**：`owner` 取自本轮 `configurable.user`，跨用户建人不留口子。
- **人数上限 20**：`count_by_user` 超限直接拒绝。
- **建人失败不影响对话**：工具返回 `{ok:false,error}`，不抛异常。
- **不递归建团队**：`agent_create` 建出来的是普通 expert，不会自动获得建人能力（只有 `is_primary` 和 team host 有）。

## 5. 施工顺序

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | `agent_create` 工具 + manager 装配 | 主智能体对话里说"招一个竞品分析师"，`agents` 表多一行 |
| 2 | `is_primary` 标记 + 前端 `/chat` 默认入口 | 打开网页直接进它，不用选人 |
| 3 | 团队页：按 `created_by_agent_id` 分组，显示"它招的人" | 页面上能看到血缘 |
| 4 | 主智能体放宽团队最少人数限制 | 0 队员也能建团队 |
| 5 | 子智能体工具化（`agent_install_subagent`） | 队员能自己装子智能体 |

## 6. 和已有改动的关系

- **Router 预设**：和团队主持的 `HOST_TOOLS_ALLOWED` 是同一思路。主智能体直接用团队主持的白名单，不再单独维护一份。
- **工单**：超级智能体派活时可以建单（`ticket_create`）并 assign 给队员；队员报进度 → 「活」页。
- **手机通道**：能力层，和本设计正交。

## 7. 未验证 / 已知限制

- `agent_create` 只做了编译与装配验证，**没有真机跑过一轮对话**；
- 新建 agent 的 workspace 初始化走 `AgentManager.create` 原流程，首次启动可能需要几秒；
- 前端入口与团队页尚未实现，当前仍从专家列表进入。

## 8. 判断层用什么模型（决策记录 2026-11-22）

**结论：先用「规则 + 已有配置模型」，不单独部署本地决策模型；但留好切换口。**

不现在本地部署的理由：

| 维度 | 现状 |
|---|---|
| 硬件 | NAS 是纯 CPU（8 核 / 15GB），1.5-3B 模型首字通常 1-3s |
| 任务 | 路由只做短判断（分类 + 选人），flash 级别模型足够 |
| 可用性 | 判断层挡在**所有**对话前面，多一个运行时 = 多一个故障点 |
| 成本 | 每条消息一次短判断，费用可以忽略 |

什么时候值得换成本地决策模型：

1. 有隐私要求（用户原话不想发给云端）；
2. 消息量大到成本敏感；
3. 实测路由延迟持续 > 800ms。

换法（已支持，无需改代码）：

1. 在模型配置里加一个本地模型（Ollama 已支持）；
2. 启动环境设置 `OCTOP_ROUTER_MODEL=<model ref>`；
3. 删掉旧的调度层 agent，下次打开对话会自动重建并绑定该模型。

## 9. 方向修正（2026-11-22，基于 DSH 实证）

读 DSH 会话日志（系统提示词 + 70 个工具）后确认：**DSH 没有独立的路由层**。
根 agent 自己判断分工，配 `subagent` / `list_agents` / `send_message` / 共享任务板 /
`create_goal` / `schedule_*`。

因此本项目的形态定为：

```
生活管家（根 agent，is_root，有人格 + 长期记忆）   ← 入口
  ├─ ask_agent / agent_create：派活、招人
  ├─ ticket_*：长任务进「活」页
  ├─ cronjob_*：定时
  └─ 成员与子智能体在团队页可见（created_by_agent_id）
```

- `is_system_router` 的隐形调度层**保留代码但不启用**，只在将来需要极速分类器时用；
- `/api/agents/home` 返回 `is_root` 的可见 agent；没有则回落第一个可见 agent；
- 工具不强行收窄（DSH 70 个工具也工作正常），等实测延迟再针对性裁剪。
