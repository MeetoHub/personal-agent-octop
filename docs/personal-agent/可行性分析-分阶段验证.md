#### 3.0.1 备份 + 试跑流程（P1 第一件事，约 2 小时）

```bash

# 2) 备份（SQLite）
cp ~/.octop/octop.db ~/.octop/octop.db.bak.$(date +%Y%m%d%H%M%S)
# 或 PostgreSQL
# pg_dump "$DATABASE_URL" > octop_$(date +%Y%m%d%H%M%S).sql

# 3) 在副本上试跑迁移
cp ~/.octop/octop.db /tmp/octop_test.db
OCTOP_DB=/tmp/octop_test.db <启动命令>
# 确认表建出、版本=26、原表行数不变

# 4) 核对原表行数没变
sqlite3 /tmp/octop_test.db "SELECT count(*) FROM agents;"
sqlite3 ~/.octop/octop.db    "SELECT count(*) FROM agents;"
# 两者必须一致

# 5) 确认无误再对正式库执行
systemctl start octop
```

#### 3.0.2 回滚方式（一行）

```bash

# psql "$DATABASE_URL" < octop_<时间戳>.sql
```

### 3.2 表结构（与现有风格对齐）

```sql
-- 026_tickets.sql
CREATE TABLE IF NOT EXISTS tickets (
    id               TEXT PRIMARY KEY,
    owner_user_id    TEXT NOT NULL,
    agent_id         TEXT NOT NULL,
    thread_id        TEXT,
    title            TEXT NOT NULL,
    goal             TEXT,
    stage            TEXT NOT NULL DEFAULT 'working',
    stage_changed_at INTEGER NOT NULL,
    report           TEXT,
    report_text      TEXT,
    assignment_id    TEXT,
    priority         INTEGER NOT NULL DEFAULT 0,
    created_at       INTEGER NOT NULL,
    updated_at       INTEGER NOT NULL,
    ended_at         INTEGER,
    end_by           TEXT
);
CREATE INDEX IF NOT EXISTS idx_tickets_owner_stage ON tickets(owner_user_id, stage);
CREATE INDEX IF NOT EXISTS idx_tickets_agent ON tickets(agent_id);
CREATE INDEX IF NOT EXISTS idx_tickets_thread ON tickets(thread_id);

CREATE TABLE IF NOT EXISTS ticket_events (
    id         TEXT PRIMARY KEY,
    ticket_id  TEXT NOT NULL,
    kind       TEXT NOT NULL,
    payload    TEXT,
    at         INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_tevents_ticket ON ticket_events(ticket_id, at);
```

**注意：时间用 INTEGER（epoch）。** 因为现有 `new_ulid` 和多数表用整数时间戳，
必须跟随，不能自造 ISO 字符串。

### 3.3 可行性：✅ 高

| 理由 | 依据 |
|---|---|
| 迁移机制是纯加文件，无需改代码 | `migrate.py:39` `_discover` 自动扫描目录 |

| SQLite + PG 双写是既定惯例 | 现有 50 个文件都是成对 |
| 纯 `CREATE TABLE IF NOT EXISTS`，幂等 | 不会破坏现有数据 |

| PG 与 SQLite 语法差异 | 中 | 分别写两份；PG 用 `BIGINT` 替代 `INTEGER` 存时间 |

### 4.2 判定函数（照抄 DSH `src/core/stage.ts` 的 first-match-wins）

```python
def resolve_stage(
    *, delivery_failed: bool, open_attention: bool,
    latest_report: str | None, has_assignment: bool,
) -> str:
    if delivery_failed:                  return "person/delivery"
    if open_attention:                   return "person/answer"
    if latest_report == "ready":         return "person/review"
    if latest_report in ("blocked", "failed"): return "person/blocked"
    if not has_assignment:               return "working/queued"
    if latest_report == "waiting":       return "idle"
    return "working"
```

**这 8 行是唯一从 DSH 借鉴的代码，逻辑已被 DSH `docs/003-execution.md` 验证。**

### 4.3 可行性：🟡 中

### 4.4 核心风险（必须提前解决）

**问题：7 个输入字段里，只有 2 个能直接拿到。**

| 输入 | 数据来源 | 状态 |
|---|---|---|
| `delivery_failed` | 无现成字段 | ❌ 需自建（ticket 表内） |
| `open_attention` | **HITL 状态，需查清在哪** | ⚠️ 待确认 |
| `latest_report` | ticket 表内 | ✅ 自建 |
| `has_assignment` | ticket 表内 | ✅ 自建 |

**所以 `open_attention` 是唯一必须从外部对接的字段。**

### 4.5 `open_attention` 的三条路

| 路 | 做法 | 可行性 | 工作量 |
|---|---|---|---|
| **A** | 从 HITL 表/内存查 | 需先定位 HITL 存储位置 | 0.5 天调研 |
| **B** | ticket 表自带 `pending_hitl` 布尔 | 完全自主，不用查外部 | 0.5 天 |
| **C** | 降级：7 态 → 3 态 | 丢精度但能跑 | 0.1 天 |

**建议 B**：ticket 表加 `pending_hitl INTEGER DEFAULT 0`，
由 HITL 事件写入时同步更新。**这样彻底解耦，不依赖 HITL 内部结构。**

### 8.4 最优路径（重要）

**不走 WS 反连，走插件系统。**

`plugins/README.md` 说明：
> `tool | ctx.tool(name, fn, description=..., config_fields=...)`

**做法：写一个 `octop-phone-tools` 插件：**

```python
# plugins/phone-tools/main.py
_pending: dict[str, asyncio.Future] = {}   # reqId -> future

async def calendar_today() -> str:
    """读手机日历（经 WS 转发到手机本地执行）"""
    req_id = new_ulid()
    fut = asyncio.get_running_loop().create_future()
    _pending[req_id] = fut
    await _send_to_phone({"type":"tool_call","reqId":req_id,"tool":"calendar.today"})
    return await asyncio.wait_for(fut, timeout=10)

def setup(ctx):
    ctx.tool("calendar_today", calendar_today, description="读今天日程")
```

**这条路的好处：**
- 完全走插件机制，**零改核心**
- 工具自动出现在工具管理页
- 可独立安装/卸载/禁用
- 符合 `plugins/` 的四 kind 设计

### 8.5 风险

| 风险 | 应对 |
|---|---|
| 手机离线时工具调用挂住 | `asyncio.wait_for` 10s 超时 |
| 多账号同时请求 | 按 `user_id + agent_id` 隔离 `_pending` |
| 权限绕过 | 手机侧二次校验（手机有最终否决权） |

## 11. 结论

### 哪些确定能做
- ✅ P1 建表（迁移机制明明白白）
- ✅ P3 REST + 隔离（端点模式现成）
- ✅ P5 前端（源码在手，token 现成）

### 哪些有不确定性但都有降级路
- 🟡 P2 → 降级 3 态
- 🟡 P4 → 降级插件中间件
- 🟡 P6 → 改走插件系统（反而更优）

### 卡住的唯一一件事
- ⚠️ P0 —— **需要你在 NAS 跑 4 条命令**

### 整体可行性判断

**方案可行，成功率约 85%。** 剩余 15% 风险集中在两处：
1. NAS 环境（wheel vs 源码）
2. harness 版本

**这两个都靠 P0 一次排查就能定性。P0 不通，后面全是空谈。**
