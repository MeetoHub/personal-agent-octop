## 0. 一句话结论

在 Octop 现有引擎（`octop-harness` + `octop-memory` + `team_manager`）之上，
**新增工单层、Router/Worker 分层、本地工具通道三层能力**，
把 68 个企业 router 按"家庭多账号"场景重新分组，
保留全部多租户能力（家人每人一个账号，数据隔离，聊天不受限）。

## 2. 多账号模型（本次新增的硬约束）

你的要求：**个人产品也要支持多账号，家里人各用各的。**

### 2.1 现有能力已足够

`infra/users/permissions.py` 的权限模型正好匹配家庭场景：

```
权限粒度 = 模块 key（settings / control / admin 三组）
admin 绕过全部
聊天、读、agent 使用永不受限
```

### 2.2 家庭角色映射（不改代码，只做角色预设）

| 角色 | 权限 | 能做什么 |
|---|---|---|
| **管理员**（你） | `admin` | 全部：管理家人、看所有人活、改模型 |
| **成员**（家人） | 空权限或 `chat` | 只能用自己的专家、自己的活、自己的记忆 |
| **访客**（临时） | 空 | 只能用被指派的专家，无记忆 |

### 2.3 数据隔离的三条线（必须验证）

| 数据 | 隔离方式 | 现状 |
|---|---|---|
| 专家（Agent） | `owner_user_id` 字段 | 已有，`agents.py` 每端点 `Depends(current_user)` |
| 记忆 | per-agent schema | 已有 |
| 活（Ticket） | **新增，按 `owner_user_id`** | 待建 |
| 会话线程 | 按 user | 已有 |

**关键设计：家人的专家默认私有。**
只有管理员显式"共享"的专家，才能被其他账号使用。

这对应 `team_manager.py` 已有的 `wire_shared_member_peers` / `_usable_shared_entry`
（`team_manager.py:2624` `list_peers`、`2670` `resolve_peer_entry`）——**跨账号共享专家已实现，复用即可。**

## 4. 模块一：工单层（你选了「建表」）

### 4.1 表结构

```sql
CREATE TABLE tickets (
    id              TEXT PRIMARY KEY,
    owner_user_id   TEXT NOT NULL,          -- 归属账号（多账号隔离）
    agent_id        TEXT NOT NULL,          -- 哪个专家在干
    thread_id       TEXT,                   -- 关联会话线程
    title           TEXT NOT NULL,          -- 用户可见的活的名字
    goal            TEXT,                   -- 原始指令
    stage           TEXT NOT NULL,          -- 7 态，见 4.2
    stage_changed_at TEXT NOT NULL,
    report          TEXT,                   -- progress/waiting/ready/blocked/failed/dropped
    report_text     TEXT,
    assignment_id   TEXT,                   -- 当前执行体
    priority        INTEGER DEFAULT 0,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    ended_at        TEXT,
    end_by          TEXT                    -- person / engine / failed
);
CREATE INDEX idx_tickets_owner_stage ON tickets(owner_user_id, stage);
CREATE INDEX idx_tickets_agent       ON tickets(agent_id);

-- 活的事件流（用于时间线展示 + 审计）
CREATE TABLE ticket_events (
    id          TEXT PRIMARY KEY,
    ticket_id   TEXT NOT NULL,
    kind        TEXT NOT NULL,   -- created/stage/report/message/approval
    payload     TEXT,            -- JSON
    at          TEXT NOT NULL
);
CREATE INDEX idx_tevents_ticket ON ticket_events(ticket_id, at);
```

### 4.2 七态判定（照抄 DSH `src/core/stage.ts:1.6KB`，从上往下第一个匹配胜出）

| 顺序 | stage | 条件 | 前端标签 |
|---|---|---|---|
| 1 | `person/delivery` | 投递失败（重试 2s→倍增到 1min） | 投递失败 |
| 2 | `person/answer` | 有等待的 HITL | **等你回答** |
| 3 | `person/review` | 最新 report = `ready` | **等你审阅** |
| 4 | `person/blocked` | report = `blocked`/`failed` 且此后无人的消息 | 受阻 / 失败 |
| 5 | `working/queued` | 无 assignment 或 pending | 排队中 |
| 6 | `idle` | report = `waiting` 或 assignment 已结束 | 等待触发 |
| 7 | `working` | 其余 | 执行中 |

**排序逻辑：前 4 态（`person/*`）全部优先。** 因为"需要人"的活必须浮到最上面。
来源：DSH `docs/003-execution.md` 的 Ticket stages 表原文。

### 4.3 REST 契约

```
GET  /api/tickets?stage=&agent_id=&limit=     列表（自动按 owner_user_id 过滤）
GET  /api/tickets/{id}                        详情 + 事件流
POST /api/tickets/{id}/resume                 恢复 blocked 的活
POST /api/tickets/{id}/stop                   停止（end_by=person）
POST /api/tickets                            手动建活（可选）
```

**每个端点必须：**
```python
from octop.api.deps import current_user, get_server
async def list_tickets(user: Any = Depends(current_user), ...):
    # 强制 owner_user_id = user.id，除非 user.is_admin
```
依据：`api/routers/agents.py:20` 的统一约定。

### 4.4 与现有系统的桥接（不新建执行体系）

| 现有 | 映射到工单 |
|---|---|
| 一次 `POST /api/agents/{id}/threads` + 对话 | 建一条 ticket，stage=`working` |
| HITL 请求（`chat/hitl/resume`） | stage → `person/answer` |
| `cron` 定时任务 | ticket 的触发源 |
| `team_manager` 派活 | ticket 的 assignment |
| 专家回复完成 | report=`ready` → `person/review` |

**关键：ticket 是现有流程的"视图 + 状态机"，不是新的执行通道。**
这样零风险，且不需要改 harness。

## 5. 模块二：Router/Worker 分层

### 5.1 问题（Octop 现状）

`infra/agents/manager.py` 给每个专家挂全部工具（45+）。
后果：每轮 3-8k token 工具定义、工具选错率 ~15%、首字延迟 1.5-3s。

### 5.2 方案（照 DSH 的 preset 分离）

DSH 原文 `docs/003-execution.md`：
> `The main Session uses dsh-superagent-router ... with **a smaller tool set for routing**.`
> `Each Ticket gets an Executor Session named worker-<ticket id> ... contains the tools needed for work`

### 5.3 落地

**新增一个 Router 专家**（`config_json.is_router = true`）：

| 项 | Router | Worker（现有专家） |
|---|---|---|
| 工具数 | 5-8 | 全部 |
| 工具清单 | `agent_list` `ask_agent` `ticket_create` `ticket_list` `memory_search` | 不变 |
| 职责 | 判断 + 分发 + 报状态 | 实际干活 |
| 模型 | 可用小模型 | 不变 |
| 记忆 | 有（知道自己派过什么） | 有 |

**三个执行档位（对应你之前确认的效果/性能最优解）：**

```
① 规则先筛（本地，0 成本，80% 情况）
   简单聊天  → Router 直接回
   含 @      → 指名派给指定专家
   多步任务  → 建 ticket

② Router 判定（20%）
   需人格    → subagent 切换（同进程，零成本）
   需专家    → ask_agent（有记忆，独立会话）
   需多专家  → ticket + team 并行

③ Worker 执行
   记忆分层检索 / 并行最多 3 路 / 长活先回执再干活
```

### 5.4 性能预期

| 指标 | 现在 | 优化后 |
|---|---|---|
| 主对话首字延迟 | 1.5-3s | **< 800ms** |
| 简单问答总耗时 | 3-5s | **1.5-2.5s** |
| 工具选准率 | ~85% | **~95%** |
| 长任务感知延迟 | 等到底 | **0**（先回执） |
| 每轮 token | 基线 | **降 40-60%** |

## 6. 模块三：本地工具通道（手机能力接入）

### 6.1 方案：WS 反连（你已确认方向）

```
手机 App ──WS 长连接──▶ NAS /api/local-tools/ws
                          │
agent 调工具 ─────────────▼
   NAS 下发 {tool, args, reqId}
                          │
                    手机本地执行
                          │
   ◀─── 回传 {reqId, result}（只回结果，不回原始数据）
```

### 6.2 为什么反连而不是被连

- 手机在 NAT 后，反连稳
- 手机握有**最终否决权**（权限检查在手机侧）
- 已有 `WS /api/agents/{id}/chat/ws` 和 `/api/notifications/ws`，协议模式现成

### 6.3 工具清单（分三批）

**第一批 · 只读（零风险，先做）**
```
contacts.search(query)      calendar.today()
calendar.create(event)      notifications.recent(n)
media.recent_photos(n)      location.current()
```

**第二批 · 控制（需 Shizuku 或无障碍）**
```
app.open(pkg)   ui.dump()   ui.tap(text)   ui.type(text)
ui.screenshot() ui.back()   ui.swipe(...)
```
**优化关键：优先 `ui.dump()`（30-60ms）而非截图+视觉（2-5s）。**

**第三批 · 组合任务**（前两批稳定后）

### 6.4 安全红线（不可让步）

| 红线 | 实现 |
|---|---|
| 不可逆操作二次确认 | 付款/发消息/删除/安装 → 强制 HITL |
| 敏感数据不出设备 | 通讯录全文/相册原图/短信不传 NAS |
| 工具分层授权 | 每个工具独立开关（复用 `enabledTools` 字段） |
| 全局熔断 | 悬浮停止按钮 + 连续 N 步无进展自动停 |

依据：DSH `docs/000-philosophy.md`
> `It stops by impact, not by effort. ... A change that needs a design decision stops with a clear question.`

## 7. 前端改造（dashboard 11.7MB / 1492 文件）

### 7.1 导航重构（你选了「允许大改」）

现有 `dashboard/src/layouts/sidebarNav.tsx` 三组：`settings` / `control` / `admin`。

**重构为家庭版四组：**

| 组 | 内容 | 谁能见 |
|---|---|---|
| **主** | 对话、活 | 所有人 |
| **团队** | 专家、子智能体、人格库 | 所有人（只显自己的） |
| **能力** | 插件、工具、技能、连接器 | 所有人 |
| **管理** | 用户、家人、模型、记忆、存储、安全 | 仅 admin |

**关键改动：导航按权限动态生成。** 现有 `permissions.py` 已有 `category: settings/control/admin`，直接映射。

### 7.2 页面增删

| 动作 | 页面 | 说明 |
|---|---|---|
| 🆕 新增 | `pages/Tickets/` | 活看板：按 7 态分组，person/* 置顶 |
| ✅ 保留 | `pages/Chat/` | 核心，1673 行 CSS 是最佳资产 |
| ✅ 保留 | `pages/Experts/` | 团队 |
| ✅ 保留 | `pages/Plugins/` | 能力扩展 |
| ✅ 保留 | 用户/家人管理 | **多账号必留**（你已确认） |
| ⬇️ 降级 | LDAP/MFA/OIDC/邀请 | 收到「高级」折叠区，家庭场景默认关 |
| ⬇️ 降级 | 云同步/备份/TLS/租户 | 同上 |
| ❌ 隐藏 | Token 统计 | 个人无意义，或改为"本月用量"简版 |

**注意：不是删除，是降级到高级区。** 因为"允许大改"≠"要砍功能"。
