## 1. 目标与边界

### 1.1 要什么

1. **本地运行**：Agent 编排、记忆、工具调度全部在手机上，不依赖常开电脑
2. **能操作 App**：不是聊天框，能真的点进微信、淘宝、日历把事办了
3. **记忆不出设备**：聊天内容、联系人、偏好留在本地 SQLite
4. **界面可变**：用户说一句话，页面布局能改
5. **离线可用**：没网时至少能记事、提醒、整理

### 1.2 明确不要什么

| 不要 | 原因 |
|---|---|
| 手机跑大模型当主力 | 见 §3.1，延迟和内存都过不去 |
| 手机当遥控器（Tobs 那条路） | 要求用户开电脑，不是"本地运行" |
| 自造 UI DSL | 2026 年已有 A2UI / MCP Apps 标准 |
| 抄 DSHBox 代码商用 | GPL-3.0，改了必须开源 |
| 抄 andee 代码 | 协议禁止白标、禁止塞进自己卖的产品 |
| 抄 nanoMuse 代码 | GPL-3.0，抄了产品就得开源 |

## 2. 架构总览（v1.1 修订）

```
┌─────────────────────────────────────────────┐
│  脸（WebView）                                │
│  ├─ 声明式渲染器（JSON schema → 组件树）        │
│  ├─ 固定组件库 18 个原子组件                    │
│  ├─ 数据源绑定（$datasource → 白名单工具）       │
│  └─ 页面快照 / 版本回退                        │
├─────────────────────────────────────────────┤
│  脑（PRoot + Debian 沙箱）                     │
│  ├─ DSH 运行时（Node.js 0.2.2-rc.2 级）        │
│  ├─ Agent 循环、上下文压缩、插件体系             │
│  ├─ 记忆层（SQLite + FTS5，参考 octop-memory）  │
│  ├─ 模型路由（守门员本地 / 主力云端）             │
│  └─ 调度（cron + Android AlarmManager 桥）     │
├─────────────────────────────────────────────┤
│  手（双通道）                                  │
│  ├─ Shizuku / ADB / root 代理（shell 级操作）   │
│  ├─ 原生小模块（无障碍，高频 UI 操作）           │
│  ├─ VirtualDisplay（后台虚拟屏，不抢焦点）        │
│  └─ 前台服务 + 电池白名单（保活）                │
└─────────────────────────────────────────────┘
                          ↕ HTTPS
                  ┌──────────────────┐
                  │ 云端 LLM API      │
                  │ (DeepSeek/Qwen)  │
                  └──────────────────┘
```

**核心原则没有变：脸可以随时换，手必须稳，脑是唯一状态源。**

变化的是脑的实现：从"Kotlin 重写"变成"直接用 DSH"，省下 2-3 个月。

## 3. 技术选型与理由

### 3.1 为什么模型必须在云端

实测数字（骁龙 8 Gen 3 + llama.cpp）：

| 指标 | 本地 7B Q4 | 云端 API |
|---|---|---|
| 输出速度 | 8–12 tok/s | 30–80 tok/s |
| 单次首字延迟 | 1.5–4 s | 0.3 s |
| 一次 agent 任务（5–15 次调用） | **1–3 分钟** | **3–8 秒** |
| 内存占用 | 4.3 GB | 0 |
| 8 GB 手机可用内存 | 4–5 GB，基本 OOM | — |

**注意区分两件事**：

- **大模型（几百 B 参数）** → 云端。手机装不下，这是物理限制
- **Agent 运行时（DSH / Node）** → 手机本地。DSHBox 已经证明可行

「把 DeepSeek 装进手机」这个说法，准确理解应该是**把 DeepSeek 的 harness 装进手机，模型仍在云端**。

本地只放守门员（Qwen3-1.7B 级，约 1 GB）：意图分类、敏感脱敏、离线兜底。

### 3.2 记忆层：参考 octop-memory，但与 harness 解耦

**选它的理由**：

1. 你机器上已经装着 `octop-memory 1.0.4`，几个月的记忆和人生档案在里面
2. MIT，可闭源商用
3. SQLite + FTS5，天然适合手机
4. 六边形架构（`domain / application / ports / adapters`），逻辑与存储分离

**重要：它跟 harness 选谁无关。**

DSH 存自己的记忆，但"记忆长什么样、怎么召回"这套设计可以照搬。做法是在沙箱里起一个独立 SQLite，DSH 通过工具调用来读写。

### 3.3 "手"的来源：双通道

v1.0 只说了原生，不完整。实测下来是两条通道分工：

| 通道 | 能力 | 速度 | 来源 |
|---|---|---|---|
| **Shizuku / ADB 代理** | shell 级：启动 App、读文件、截图、批量操作 | 中 | 参考 DSHBox 实现 |
| **原生无障碍服务** | 读 UI 树、精确点击、文本输入 | 快（毫秒级） | 参考 Droidance（Apache-2.0） |

**分工原则**：

```
粗粒度、偶尔做 → Shizuku shell（am/pm/input/screencap）
细粒度、高频做 → 原生无障碍（uiautomator dump 一次几百毫秒，太慢）
```

这也是 DSHBox 的做法——它把 Shizuku 能力做成 40 项可审批清单 + 受保护应用名单，这个设计值得直接学。

### 3.4 插件体系：跟 DSH 走（v2.0 重写）

DSH 是 MIT、"一切皆插件"，插件通过 `dsh.bundle.patch` 挂到 profile 上，**零核心 patch** 就能做出完整产品。对我们来说这意味着两件事：手机上那套 skills 不必自己从零写，生态里已经有的可以直接吃；商用时的企业能力也不必 fork 源码。

#### 3.4.1 生态真实规模（口径要小心）

| 口径 | 数字 | 说明 |
|---|---|---|
| 官方仓库 | **281.6k ★ / 34.8k fork** | MIT，2026-08-13 开源 |
| GitHub `dsh-plugin` topic | **2300 ~ 7800+**（不同来源差异大） | **topic 是自贴标签，不等于能装** |
| 目录站收录 | 1117 ~ 1700+ | dshpluginhub.dev / mydsh.dev / dsplugin / 52DSH / Oh-My-DSH |

差额本身是信息：正因为"贴了 topic 装不上"很常见（`package.json` 里没有有效的 `dsh.bundle` 声明，复制安装命令会装空），才冒出一批专门做 manifest 校验和实测的目录站。**选插件前先确认它有有效 bundle，别看 star。**

#### 3.4.2 四层结构：越往下越值得投入

| 层 | 改什么 | 代表 | 长期价值 |
|---|---|---|---|
| 底座层 | Cordis 服务接缝（`ctx.fs` / `ctx.llm` / tools） | 官方 `@deepseek-ai/dsh-*` 系列 | 高，但已饱和 |
| 能力层 | 补模型短板 | modlens、vision-toolkit、git-workflow | 中，易被模型升级吃掉 |
| **治理层** | **流程资产化** | turn-rewind、hooks、dsh_workflow | **最高** |
| 生态层 | 接入别的生态 | pi2dsh、chat-import、各类 bridge | 高，但门槛也高 |

**判断依据**：能力层插件在赌"模型一直不会这个"；治理层插件在攒"用户自己的流程和状态"。后者才沉淀资产。

#### 3.4.3 手机端选型：装什么、不装什么

**✅ 该装（按优先级）**

| 插件 | 为什么手机端特别需要 |
|---|---|
| **modlens** 或 `pi-vision` | **手机 agent 的第一需求是看懂屏幕**。DSH 是纯文本模型，没有视觉就永远在瞎点。见 §3.4.4 |
| **dsh-turn-rewind** | 基于持久化 Change Ledger 的对话+代码回退。手机上 agent 误操作（删错、发错）比桌面上更难挽回 |
| **dsh-plugin-hooks** | Claude Code 风格 pre/post-tool 钩子，pre-tool 非零退出即**阻断**该次工具调用。正好用来做"发消息/付款前必须过审"的硬闸门 |

**⚠️ 观察，暂不装**

| 插件 | 原因 |
|---|---|
| `pi2dsh`（Pi 生态兼容层） | 架构很漂亮（一次实现 Host ABI，不逐包适配），能把整个 Pi 生态带进来。但 Pi 扩展以**宿主代码**身份运行，可读写文件/执行命令；52DSH 核验标注"配置难度较高、源码已审阅未实测"。手机上权限面太大 |
| `dsh_workflow` | 设计极扎实（run snapshot + **effect cache 只续跑未完成部分** + capability-only VM + 审批分级），但它是给桌面长流程准备的，手机端跑不动。**抄它的思路，不装它** |
| `dsh-darwin`（自进化） | sentinel 挖会话日志→forge 合成技能，概念激进但实验性质，且手机端日志量不足以喂它 |

**❌ 不适用**

`dsh-browser`（Chrome 侧边栏扩展）——手机浏览器没有扩展体系，这条路在手机上不存在。手机上的"手"只能是 Shizuku + 无障碍（见 §3.3）。

#### 3.4.4 手机端的核心缺口：它看不懂屏幕

这条值得单独拎出来，因为 v1.1 漏了。

**DSH 用的 DeepSeek 是纯文本模型。** 而手机 agent 的循环是"看屏幕 → 决定 → 点"，第一步就要视觉。现在 uiautomator dump 只能拿到控件树文本，遇到这些就废了：

- 图片里的文字（快递单号、验证码、海报）
- 自绘 UI（微信、小红书大量页面 dump 不出结构）
- 报错弹窗的截图
- 用户直接甩一张图问"这个怎么办"

**解法**（社区已经验证过两条）：

1. **modlens** —— 加一个 `modlens_read_image` 原生工具，把图翻成结构化文本证据（OCR + 版面），再喂给 DeepSeek。本质是"请个会看图的朋友在旁边念"
2. **pi-vision 伴生路由** —— 每条 text-only 模型路由自动获得一个 `-vision` 伴生分组，图片块在进入 DeepSeek adapter **之前**被移除，只把分析后的文字送进去

**这是 P0 阶段就要验证的能力，不是 P2 的锦上添花。** 没有它，"能操作 App"这个目标基本不成立。

#### 3.4.5 版本必须锁死

DSH 还在 developer preview，**RC 之间接口会 break**。实证：`dsh-plugin-agent-workflow` 的兼容表是 `0.1.x → dsh 0.1.0-rc.8`、`0.2.x → 0.1.5-alpha.1`、`0.3.x → 0.2.0-rc.2`。升级 DSH 必须同步换插件版本。

**规矩**：所有插件安装命令写死版本号，禁止 `@latest`。P0 阶段以 `0.2.2-rc.5` 为基线。

#### 3.4.6 manifest 长什么样

```json
{
  "name": "daily-brief",
  "version": "1.0.0",
  "tools": [
    {
      "name": "get_schedule",
      "description": "读取今日日程",
      "parameters": { "type": "object", "properties": {} }
    }
  ],
  "ui": { "entry": "ui/index.html", "schema": "ui/schema.json" },
  "permissions": ["calendar.read", "notification.read"]
}
```

一条铁律：**UI 只能调用 manifest 里声明过的工具。**

#### 3.4.7 插件的真实权限面（别忽视）

社区插件**以你的完整权限运行**——能读写文件、执行命令、访问外部服务。目录站的"已收录"只是收录，不是审计。社区已出现过"topic 里有仓、但 bundle 无效、安装命令装空"的情况。

三条规矩：

1. 装之前看 `package.json` 的 `dsh.bundle` 声明和 `scripts` 字段
2. 只从**锁定版本或固定 commit** 装，不跟 default 分支
3. 新插件先在独立 profile 里跑通，再进主工作区

### 3.5 为什么 harness 底层选 DSH，不选 octop-harness

这是 v1.1 最大的改动。

| 维度 | **DSH** | octop-harness |
|---|---|---|
| 手机上跑起来的先例 | ✅ **DSHBox v1.5.5 实证** | ❌ 无 |
| 生态 | **282,728 ★** | 160 ★ |
| 插件可复用 | 海量 | 几乎为零 |
| 你的经验 | **你改过 DSH 做企业版** | 无 |
| Android 运行时难度 | **Node.js 纯 JS，丢进去就能跑** | Python，C 扩展在 bionic 上要重编 |
| 许可 | **MIT，可商用** | MIT，可商用 |

**决定性的是第二、四、五条。**

尤其第五条容易被低估：Python 在 Android 上痛苦一个量级。numpy、pydantic、lz4 这些带 C 扩展的包，Termux 里能装是因为人家替你编好了 arm64+bionic 版本；你自己做 APK 时要自己维护编译链。Node 纯 JS 没这问题。

**一句话**：DSH 是已经有人帮你验证过能在手机上跑的那个，octop-harness 是理论上能跑但没人验证过的那个。创业不该拿这个赌。

### 3.6 生成式 UI：选声明式，不选自造

2026 年四个标准：

| 标准 | 出品方 | 渲染 | 移动端 |
|---|---|---|---|
| **MCP Apps** | Anthropic（2026-01，MCP 首个官方扩展） | inline HTML / web components / iframe | WebView |
| **A2UI** | Google | 声明式，面向移动端与桌面 | 最贴合 |
| Apps SDK | OpenAI | ChatGPT 专有 | ❌ |
| AG-UI | CopilotKit | React | ❌ |

三种模式，选第二档：

1. 静态组件 —— 死板，满足不了"可变"
2. **声明式（JSON → 组件树）—— 选这个**：灵活性、一致性、速度的最佳平衡
3. 开放式（LLM 直写 HTML/JS）—— 需重沙箱，P2 以后再考虑

### 3.7 保活：真正的硬骨头

比模型难十倍。五层防御：

1. **前台服务 + 常驻通知**
2. **电池优化白名单**（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）
3. **厂商自启白名单**——小米/华为/OPPO/vivo 各不相同，做引导页
4. **无障碍服务本身不易被 kill**——DSHBox / andee / Droidance 都靠这个
5. **AlarmManager 精确定时兜底**

先支持小米、华为，其他 ROM 出问题再补。

## 4. DSHBox 实证盘点（新增）

### 4.1 它是什么

`WSK-build/DSHBox` ｜ 688 ★ ｜ **GPL-3.0** ｜ Android 10+ / ARM64

把 DSH 完整跑在手机上，**无需 Root、无需 Termux**。

| 项 | 实况 |
|---|---|
| 运行环境 | **PRoot + Debian 沙箱 + Node.js**，内置 DSH `0.2.2-rc.2` 运行层 |
| 首次准备 | 分步安装精简 Debian 与 Node.js，支持多镜像源、失败重试、离线导入 |
| 包体 | 系统 WebView 版 155 MB / 内置 Gecko 版 244 MB（同包名同签名，可互覆） |
| 手机操控 | Shizuku / ADB / root **三通道**，40 项能力逐项审批 |
| 安全设计 | 受保护应用名单（不许启动/读取/操作），审批等待期间二次拦截 |
| 屏幕 | 虚拟屏实时预览：点按、滑动、返回、主页、旋转、移主屏、释放 |
| 其他 | 终端、文件管理、浏览器自动化、设备状态、录音 |

### 4.2 它证明了什么

1. ✅ **Node + DSH 能在 Android 上跑起来**（不是理论，是发版产品）
2. ✅ **Shizuku 代理能让沙箱进程操作手机**（v1.0 的判断在此修正）
3. ✅ **虚拟屏方案可用**（后台操作不抢用户焦点）
4. ✅ **审批 + 白名单这套安全设计是必要的**，人家已经踩过

### 4.3 它的局限

| 局限 | 影响 |
|---|---|
| **GPL-3.0** | 改了必须开源，**不能闭源商用** |
| 包体 155–244 MB | 比原生 App 大一个量级 |
| PRoot 性能损失 | 20–40%，冷启动慢 |
| 内存占用高 | Node + 浏览器内核，中端机吃力 |
| 仅 ARM64、Android 10+ | 覆盖有限 |
| 首次要装 Debian + Node | 几百 MB 下载，劝退普通用户 |

### 4.4 一个值得你自己回答的问题

> 你的手机端 DSH 昨天（2026-11-16）刚退役，你说"之后不怎么跟他对话"。

这件事本身就是最真实的用户反馈。**在选型前值得想清楚：当时为什么不用了？**

是启动太慢？耗电？还是"手机上用 agent"这件事本身没那么需要？

如果是第三种，那这套方案再精致也没用——**先搞清楚需求真不真，再谈架构。**

## 5. 核心模块设计

### 5.1 数据模型（SQLite）

四张核心表 + 一张 FTS：

```sql
-- 原始事件（不可变，只追加）
CREATE TABLE episodes (
  id TEXT PRIMARY KEY, session_id TEXT NOT NULL,
  role TEXT NOT NULL, content TEXT NOT NULL,
  created_at INTEGER NOT NULL, meta TEXT
);

-- 提炼后的事实
CREATE TABLE atoms (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,          -- Fact / Preference / Decision / Task
  topic TEXT, content TEXT NOT NULL,
  confidence REAL DEFAULT 1.0,
  source_ids TEXT,             -- JSON，回溯到 episodes
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);

-- 实体页（人物/地点/项目/设备）
CREATE TABLE entities (
  id TEXT PRIMARY KEY, type TEXT NOT NULL, name TEXT NOT NULL,
  attrs TEXT, updated_at INTEGER NOT NULL
);

-- 实体关系
CREATE TABLE relations (
  src_id TEXT NOT NULL, dst_id TEXT NOT NULL,
  predicate TEXT NOT NULL, weight REAL DEFAULT 1.0,
  PRIMARY KEY (src_id, dst_id, predicate)
);

-- 全文检索
CREATE VIRTUAL TABLE atoms_fts USING fts5(
  content, topic, content='atoms', content_rowid='rowid'
);
```

**三级召回**（从便宜到贵）：

```
1. FTS5 关键词召回      → 快，覆盖 70%
2. 实体图扩散            → 中，覆盖 20%
3. 向量语义召回（可选）  → 慢，兜底 10%
```

先用前两级，向量（sqlite-vec）留接口后期加。

### 5.2 Agent 循环

```
用户输入
  → 守门员分类（要不要唤醒大模型？哪个技能？）
  → 记忆召回（三级）
  → 组装上下文（系统提示 + 召回 + 工具清单 + 近期对话）
  → 云端 LLM
  → 工具调用？（是 → 执行 → 回填 → 再问模型）
  → 输出文本 / 生成 UI schema
  → 写回记忆
```

关键：**上下文压缩**。手机端窗口小、token 贵，必须滑动窗口 + 摘要。

### 5.4 安全沙箱

```
WebView
 ├─ JS 侧：只允许 host.invoke(toolName, args)
 │          toolName ∈ manifest.tools（原生侧二次校验）
 ├─ 禁止：file:// 跨域、任意网络、eval、远程脚本
 ├─ CSP：default-src 'self'; script-src 'self'
 └─ 原生侧：签名校验 + 频次限流 + 参数 Schema 校验
```

**绝不做**：不暴露通用 `exec`、不暴露文件系统全路径、不暴露通讯录裸数据。

## 9. 许可陷阱（新增，商用必读）

这是整份文档里最容易踩雷的一节。

| 组件 | 协议 | 能闭源商用？ | 说明 |
|---|---|---|---|
| **DSH 本体** | **MIT** | ✅ **可以** | 可打进你卖的 APK |
| **DSHBox** | **GPL-3.0** | ❌ **不可以** | 改了必须开源 |
| octop-memory | MIT | ✅ | 保留版权声明 |
| Droidance | Apache-2.0 | ✅ | 保留 LICENSE + NOTICE |
| A2UI / MCP Apps | 标准规范 | ✅ | 按规范署名 |
| andee | Apache2.0 + 四条附加 | ⚠️ 极有限 | 不能白标、不能塞进产品 |
| nanoMuse | GPL-3.0 | ❌ | 必须开源衍生 |

### 关键结论

> **DSH 是 MIT，DSHBox 是 GPL。**
>
> 你不能抄 DSHBox 的代码去卖，但可以**照着它的思路**，用 MIT 的 DSH 自己搭壳。

这可能正好解你之前那个结——你改过 DSH 想做企业版，卡在商业化。**DSH 的 MIT 协议给了你商业化的法律基础**，缺的不是许可，是产品形态。

### 红线

- DSHBox、nanoMuse 的代码：**一行都不要复制进商用产品**
- andee：**只读思路**，避免产生衍生作品
- 参考实现的做法：读懂逻辑 → 自己重写 → 保留自己的版权声明
