# 开发流程（2026-11-21 起生效）

这份文档解决的是过去两天真实踩到的坑：三份源码树互不同步、生产与仓库版本不一致、部署漏备份、CI 从没跑过。

---

## 0. 三条铁律

1. **只有一个源码真相：本仓库。** 任何改动先落到这里，再从仓库部署。不允许"直接改 NAS 再补提交"。
2. **生产不是本仓库的 HEAD。** 生产跑 `v1.0.3b6`，仓库基于 `v1.0.3b7`。两者差异来自上游漂移，不来自我们的补丁（见 §4）。
3. **动生产必须：先备份 → 再上传 → 双端 SHA 比对 → health 检查 → 打印回滚命令。** 用 `deploy/nas/deploy.sh`，不要手搓命令。

## 1. 目录角色

| 位置 | 角色 | 允许的操作 |
|---|---|---|
| 本仓库（clone 到本地） | **唯一源码真相**：后端 `src/octop/`、手机端 `android/`、文档 `docs/personal-agent/` | 所有开发都在这里提交 |
| `05-Octop本体/` | 历史参考（origin 指向上游，含未提交的早期补丁） | **只读**，不要再改 |
| `02-Octop源码/octop-mobile/` | 早期 App 工作区 | 冻结，代码已快照进 `android/` |
| NAS `/vol1/@appcenter/octop-native/site-packages/octop` | 生产运行目录 | 只有 `deploy.sh` 能写 |

> 迁移期如果还要用旧目录继续开发，先把它和本仓库 `diff` 一遍，确认没有遗漏再提交。

## 2. 分支与标签

| 分支/标签 | 用途 |
|---|---|
| `main` | 可部署状态。**不直接 push**，一律走 PR（上游 CI 只在 PR 上跑） |
| `feat/<主题>` | 功能开发 |
| `fix/<主题>` | 修复 |
| `deploy-YYYYMMDD-N` | 每次部署后打标签，记录"这一刻生产是什么" |

紧急回滚可以直接 `git revert` 后推 main，事后补 PR。

## 3. 日常流程

### 3.1 改后端（`src/octop/`）

```bash
git switch -c feat/xxx
# 改代码
python -m compileall -q src/octop/infra/phone src/octop/infra/tickets src/octop/api
git commit -m "feat(phone): ..."
git push -u origin feat/xxx
gh pr create --fill
```

合并前必须：PR 的 CI 绿 + 本地 `make lint`（至少 compileall）通过。

### 3.2 改手机端（`android/`）

```bash
cd android
./gradlew :app:assembleDebug      # 或 compileDebugKotlin
```

真机验证后才合并。截图放 `docs/personal-agent/screenshots/`（脱敏）。

### 3.3 改文档

文档只放 `docs/personal-agent/`。工作区 `01-方案文档/` 里的同名文件不再维护，避免双份漂移。

## 4. 生产基线与版本对应（重要）

| | 版本 | 说明 |
|---|---|---|
| 仓库基线 | 上游 `v1.0.3b7`（commit `30f4aec`） | 可随时 `git merge upstream/main` |
| 生产 NAS | 上游 `v1.0.3b6` + 同一组补丁 | 通过 FPK 安装，未升级到 b7 |

**已验证**：取 `v1.0.3b6` 的 `manager.py` 与生产对比，差异**恰好是 P6 的 3 处**（212581→210313 的差额全部来自 b6/b7 漂移）。
`app.py` 在 b6/b7 中内容相同，所以生产与仓库的 `app.py` SHA 一致。

这意味着：

- 从仓库部署到生产：**只有补丁涉及的 14 个文件需要上传**，其余文件不要动。
- 上游一旦升级到 b7，`manager.py` 的补丁锚点需要重新定位（`grep -n` 找，别按行号硬改）。
- 复现生产：`git checkout v1.0.3b6` + 应用 `deploy/nas/files.txt` 里的补丁。

## 5. 部署

```bash
# 1) 只读核对：本地文件 vs 生产文件，不写任何东西
NAS_HOST=<你的 NAS 地址> NAS_USER=<用户名> SSH_KEY=~/.ssh/id_ed25519 \
  ./deploy/nas/deploy.sh --check

# 2) 正式部署：自动备份 → 转 LF → 上传 → 双端 SHA → health
NAS_HOST=... NAS_USER=... ./deploy/nas/deploy.sh --apply

# 3) 需要重启服务时（会要求 NAS_SUDO_PASS）
NAS_HOST=... NAS_USER=... NAS_SUDO_PASS=... ./deploy/nas/deploy.sh --apply --restart
```

脚本保证的事（也是手工时代漏掉过的）：

- 部署前把远端现有文件打包到 `patches/backup-<时间戳>/`；
- 所有上传文件强制 LF（`grep -c $'\r'` 必须为 0）；
- 上传后逐文件比对 SHA256，不一致立即停止；
- 打印可直接复制的回滚命令。

**什么时候需要重启**：改了 `*.py` 就必须重启；只跑迁移不用。

---

## 6. 上游同步

```bash
git fetch upstream main
git merge upstream/main
```

频率：上游发版后 3 天内，或每两周一次。
冲突高发文件：`api/app.py`、`infra/agents/manager.py`、`infra/errors.py`（都是我们插过行的）。解决原则：**以上游为底，重新插入我们的行**，不要整文件覆盖。

## 7. 备份

| 级别 | 时机 | 位置 |
|---|---|---|
| 部署前快照 | 每次 `deploy.sh --apply` 自动 | NAS `patches/backup-<ts>/` |
| 补丁基线 | 每批补丁上线时手工留一份 | NAS `patches/p6-baseline-YYYY-MM-DD/` |
| 全量备份 | 每月 / 大改前 | Windows `G:\个人智能体开发-backup-<ts>` |

数据库备份**必须**用 `sqlite3` 的 backup API 或 `VACUUM INTO`，**不能 `cp`**（WAL 模式下会得到不完整副本）。现成脚本：`patches/backup.sh`。

## 8. 提交规范

```
type(scope): 一句话说明

feat(phone): 手机反向通道只读工具
fix(tickets): PATCH 端点区分未传与显式 null
docs: 开发流程
chore: 依赖与配置
deploy: 2026-11-21 生产部署记录
```

部署请单独提交并打 tag，方便日后 `git diff deploy-20261121-1..v1.0.3b6` 看出生产实际内容。

## 9. 保密

- 密码、SSH 私钥、token、内网地址**不进仓库**。文档一律用 `<密码>`、`100.x.x.x`、`<令牌>` 占位。
- 仓库是 public 的，提交前自查：
  ```bash
  git diff --cached | grep -nE "密码|password|passwd|BEGIN OPENSSH|token=" 
  ```
- 发现误提交：立刻轮换凭据，再 `git filter-repo` 清历史；只删文件不够。
