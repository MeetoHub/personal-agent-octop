# 追踪 Octop 上游

- 上游仓库：<https://github.com/TencentCloud/Octop>
- 我们的基线：`1.0.3b7`，commit `30f4aec`

## 原则

本仓库**只存增量补丁**，不存整份上游源码。`nas/patches/` 里每个 `.py` 文件都是“相对上游某个版本的完整替换文件”，其 SHA256、目标路径、部署纪律记录在 `nas/patches/MANIFEST.md`。

## 当前补丁清单

| 补丁 | 目标路径（相对 Octop 包根） | 作用 |
|------|------------------------------|------|
| `stage.py` | `infra/tickets/stage.py` | 工单状态机（7 阶段单一真源） |
| `store.py` | `infra/tickets/store.py` | 工单存储层 |
| `tickets.py` | `api/routers/tickets.py` | 工单 HTTP 路由（12 端点） |
| `errors.py`（见 MANIFEST） | `infra/errors.py` | 新增 `TICKET_NOT_FOUND` 错误码 |
| `app.py`（见 MANIFEST） | `api/app.py` | 挂载 tickets 路由 |
| `backup.sh` / `restore.sh` | 数据脚本 | SQLite 备份/恢复（WAL 安全） |

数据库迁移：`nas/migrations/026_tickets.sql`（SQLite）、`026_tickets.pg.sql`（PostgreSQL）。

## 上游升级流程

1. 拉取新版本到工作区：
   ```bash
   git clone https://github.com/TencentCloud/Octop.git
   cd Octop && git checkout <新版本 tag>
   ```
2. 对照 `MANIFEST.md`，逐个核对补丁目标文件在新版里是否改动：
   - 若目标文件未变：直接复用我们的补丁文件。
   - 若目标文件变了：人工 diff 合并我们的改动到新版，重新生成 SHA256 并更新 MANIFEST。
3. 应用迁移（幂等，无需重启服务）：
   ```bash
   # 按 nas/README.md 的迁移命令执行
   ```
4. 跑回归：`nas/tests/` 下的 `t_stage.py`、`t_longtask.py`、`t_store.py`，以及 HTTP 冒烟。
5. 生产部署前先备份（见 `nas/deploy/`），再按 MANIFEST 的重启流程操作。

## 纪律（血泪教训）

- 行尾必须是 **LF**：`core.autocrlf=true` 环境下 `.py/.sh/.sql` 上传前要转 LF，并校验 `grep -c $'\r'` = 0。
- 备份只能用 SQLite **backup API / VACUUM INTO**，绝不能裸 `cp octop.db`（WAL 会丢数据）。
- 生产文件权限要保留（如 `errors.py` 700、`store.py` 644、`tickets.py` 644、`app.py` 700）。
- `app.routes` 因 `_IncludedRouter(path=None)` 看不到路由，验证要用 `app.openapi()['paths']` + 真实 HTTP。
