## 一、出发点：为什么非做不可

**【实证】当前痛点**：Octop 跑在家里的飞牛 NAS 上，24 小时常驻，但它**碰不到手机**——

- 看不了手机信息、通讯录
- 读不了短信、通知
- 点不了手机上的 App

所以手机端必须有一个**自己跑在手机上**的 agent，而不是 NAS 那个再包一层。

## 三、盘过的候选方案

### 1. nanoMuse（浙大开源）★ 重点关注

| 项 | 值 |
|---|---|
| 仓库 | `github.com/nano-muse/nanoMuse` |
| 官网 | nanomuse.cn |
| 团队 | 浙江大学 Guangyi Liu / Yong Liu / Jiangning Zhang（有论文） |
| 许可 | **GPL-3.0-or-later** ← 注意：传染性，二开必须开源 |
| 技术栈 | **Swift**，基于 **OpenMinis 1.13** |
| Stars | 2.7k |
| APK | 1.0.9 / 37.7 MB / **仅 arm64-v8a** |
| 内部结构 | 含 `lib/minis-mcp-cli/` → 属 Minis 生态 |

**产品设计（这几点值得抄）**
- 一个账号打通手机 / 桌面 / 网页
- **每台设备本地跑自己的记忆 + Sentinel 安全层**（符合你要的"本地"）
- 多设备靠**可自建 Relay 中继**
- **不可撤销操作（删除 / 发送 / 付款）会先停下问人** ← 安全阀设计

### 3. Avibe —— ❌ 已排除

**【实证】没有安卓版。** 最新正式版 v3.2.6 只有 macOS 和 Windows 桌面安装包，手机端仅 iPhone App（App Store）。

### 4. 自研 App + Shizuku 万能通道 ★ 你实际倾向的路线

**为什么现成的 Minis 系满足不了你**：

现成 App 的能力边界 = 它自己实现了哪些 MCP 工具。想读短信、读通知、跑 `adb shell`，这些都需要**系统级权限**，一般商业 App 不会给。所以第 3/4/5/6 条要求，**只有自研才能全部满足**。

**Shizuku 是什么**：安卓上一次 ADB 授权（或用无线调试配对），长期拿到 shell 权限，不受普通 App 沙箱限制。**一次授权，全局可用，不需要为每个 App 单独适配。**

**架构（你的原话）**：

```
Agent（LLM 决策层）
    │
    └── 万能通道（Shizuku shell）
          ├── phone.shell     ← 执行任意 shell 命令
          ├── screenshot      ← 截屏
          ├── ui_dump         ← 读 UI 树（替代无障碍服务）
          └── 少量快捷封装     ← 高频操作才封装
```

**这个设计的价值**：新需求不用改 App，写一条 shell 命令就行。适配成本从"每个 App 一套代码"降到"一句命令"。

## 五、还没定的事（需要你拍板）

1. **要不要先装 nanoMuse 试一周？** 它现成能用，能快速验证"手机 agent 到底好不好用"，但拿不到短信/通知权限。
2. **自研的话，底座选什么？** 从零写，还是在 nanoMuse / OpenMinis 上二开？二开会撞上 GPL-3.0（必须开源）。
3. **模型放哪？** 全本地跑（端侧小模型，能力有限）还是本地跑流程 + 云端大模型做决策（要联网，跟"本地"要求有冲突）。
4. **人机边界**：哪些操作必须停下来问人？（nanoMuse 的答案是删除/发送/付款，你要不要更严）
5. **和 Octop 的关系**：手机 agent 是独立体，还是 NAS 上这个小乐的"手机分身"、共用一套记忆？

## 六、我的建议（供参考，不是结论）

**短期**：先装 nanoMuse 1.0.9 实测两天，重点看三件事——它能不能读到通知、MCP 工具能调多深、断网还能不能用。这比看文档快。

**中期**：如果 nanoMuse 卡在权限上（大概率），走自研 + Shizuku。第一步不是写 Agent，而是**先跑通 Shizuku + phone.shell + screenshot + ui_dump 这四条打通**，写个命令行 demo 证明"能读通知、能截屏、能点按"。这一步通了，上面接什么模型都好办。

**别做的事**：不要一上来就设计 UI。你自己说过的——"产品不要对话页，要 today 式面板"，那是第二步的事。
